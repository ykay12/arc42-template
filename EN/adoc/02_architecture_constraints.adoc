== Architecture Constraints

The following constraints were identified from the Business Requirements Document and directly shaped all architectural decisions.

[options="header",cols="1,2,3"]
|===
|ID|Constraint|Background / Motivation

|TC_1
|Cross-platform mobile support: iOS and Android
|The startup targets a global audience of millennials and Gen Z users on both major mobile platforms. Native apps (Swift for iOS, Kotlin for Android) are built to maximise rendering performance and platform-native UX for an image-heavy product, accepting the higher effort of maintaining two codebases.

|TC_2
|The architecture must support integration with Pixlr
|Advanced editing and filtering tools are a core business requirement. Since these capabilities are partially outsourced to Pixlr, the system architecture must allow secure API communication, error handling, and future replacement or extension of third-party services.

|TC_3
|The application must comply with relevant security and privacy regulations such as GDPR
|The app stores personal user accounts, images, comments, and subscription information. As the app operates globally and targets users in Europe, protecting user privacy and ensuring secure authentication and data storage are mandatory.

|TC_4
|The architecture must support scalable cloud-based infrastructure
|The business goal is to attract a large and engaged user base. Image sharing platforms require high storage capacity, fast content delivery, and responsive feeds. The architecture must therefore support horizontal scaling and optimized media delivery, capable of handling increasing image uploads, user interactions, and global traffic with minimal loading times.

|TC_5
|The system architecture must support freemium functionality, subscription management, and future advertising integrations
|The startup's business model depends on monthly and annual premium subscriptions, with possible future sponsored content and advertising. The architecture must therefore separate free and premium features securely and allow integration with payment providers and advertising systems later on.

|===

=== Organisational Constraints
 
[options="header",cols="1,2,3"]
|===
| ID | Constraint | Rationale

| OC_1
| GDPR compliance mandatory
| Users expected globally; EU users require GDPR-compliant data handling, right-to-erasure support, and data residency options.

| OC_2
| App Store and Play Store approval pipeline
| All releases must pass Apple and Google review; no undisclosed third-party data sharing.
|===
